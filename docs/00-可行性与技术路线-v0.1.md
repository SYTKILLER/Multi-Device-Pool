## 0. 结论速览（15 行）

1. **技术可行，但必须改一个前提**：可分布式的是**工具执行**，不是 **agent 循环**。"一个大脑 + N 只手"能做且今天就能做；"多个大脑互相协商"是另一个问题，先不要碰。
2. **不需要 fork DSH**。插件可 `ctx.tools.register` 注册工具；`dsh-mcp-client` 支持 stdio / Streamable HTTP，且官方有 per-session 挂载范例（`dsh-acp/lib/index.js:216`）。DSH 自己**不能**当 MCP server（全树 grep 0 命中）。
3. **现有工程最值钱的是"设计"不是"代码"**：把手机当"本机浏览器"的 L4 隧道、presence-only 信令、DTLS 指纹 pin、TURN 兜底、11 字节帧 + 信用流控，这些在池里全部成立；但**契约的 pair 模型是 1:1 写死的**（契约 §4.3 ④⑤；`hub.go:46-70`），不是加字段能解决的事。
4. **别自研 UDP 可靠层**。项目已经在用 WebRTC/ICE/UDP，这正是业界答案；公开大规模实测打洞条件成功率 **70%±7.1%**（[arXiv:2604.12484](https://arxiv.org/abs/2604.12484)），瓶颈是 NAT 类型与 RTT 同步，不是协议选型。
5. **别做"多设备像一块 PC 的多个磁盘"的分布式文件系统**。工具命名空间层面可以做到；OS 挂载层面（FUSE/WinFsp）在抖动链路上每次 `stat` 都是一次 RTT，且手机根本挂不了。业界（VS Code Remote / Coder / Mutagen）也都不这么做——它们做的是**远程执行 + 工作区同步**。
6. **公网兜底的硬顶是 3Mbps**：`bps-capacity=350000 B/s`、`max-bps=250000 B/s`（`new_docs/02` §4）→ 满速仅 **≈1.4 路**；N 节点全走中继时每节点只有 **350/N KB/s**。中继只配做控制面兜底，文件搬运必须走 P2P 或经主节点转发。
7. **手机不能当执行节点**：鸿蒙/ iOS 三方应用进程挂起即断网、不能常驻长连接（`Document/remote-app-research/07` §2.4）；鸿蒙三方也没有通用 shell/exec 能力。手机＝**入口与 UI**，PC/服务器＝**执行节点**。
8. **"随时切换主节点"要拆成两件事**：切换对话入口（UI 漫游）几乎免费——DSH 本来就支持多客户端并发、事件广播、审批首答生效；迁移 agent 宿主（大脑搬家）昂贵且多数场景不需要，只能做成 PC↔PC 的**冷迁移**。
9. **鸿蒙软总线 API 借不到，只能借思想**：DSoftBus 无公开 ArkTS API，`distributedDataObject` 官方限定场景且 ≤3 设备/150 KB。可借的是：近场优先+云兜底发现、PIN 短期配对+持久可信表、能力清单、迁移＝状态快照重放。
10. **最硬的三个约束**：①契约 1:1 pair；②3Mbps 中继；③链路本身还不稳（`ISS-009`/`ISS-014` 未闭环，实测约 20% 时间隧道死，池可用性上界 ≈ `0.8^N`）。
11. **建议的落地顺序**：先用 SSH/Tailscale 把"池的价值"验证出来（2–3 周，零契约改动），再决定要不要为"免配置组网"付出契约 v2.0 的代价。
12. **市面没有完全相同的产品**，但每一层都有强替代品；真正空白的是"自有设备 + agent 单会话 + 跨节点工具/文件 + 主节点可换"。这个空白之所以存在，主要不是技术难，而是**云沙箱更省事、多设备用户是窄众**。
13. **最大风险不在技术**，在安全模型：一个大脑能对全部设备执行任意命令，而 DSH 至今没有设备表、没有按设备撤销、MCP 工具**默认不审批**。池层必须自带信任与授权，这是产品级工作量，不是插件补丁。
14. **工期量级**（单人、熟手、不含链路修复）：单节点闭环 1–2 周；池骨架 2–3 周；接现有隧道 3–4 周；接力/多入口 2–3 周。可用版本按 2–3 个月估。
15. **一句话判断**：这个构想**值得做，但应当作为"一个大脑 + 多执行面"的产品来立项，而不是"分布式 agent 系统"**；技术上 70% 是复用与集成，30% 是新的池语义与安全，而链路稳定性是必须先付的账。

## 1. 把构想拆成七个可判定的命题

原构想是一段愿景；评审必须把它拆成能判"能/不能/有条件能"的命题。逐条判定如下。

| # | 命题 | 判定 | 依据 / 说明 |
|---|---|---|---|
| P1 | 一个 agent 能同时操作多台设备 | **能** | 插件可注册工具（`dsh-tools/lib/types/index.d.ts:596`）；MCP client 可挂 N 个远端 server；工具名按 server 加 `mcp__<server>__<tool>` 命名空间 |
| P2 | 多设备像一块 PC 的多个磁盘 | **部分能** | 工具层能（`node` 参数或工具名前缀）；OS 挂载层不建议（延迟、手机不可挂、失败语义）。见 §5.3 |
| P3 | 远程过程像调用本地过程 | **语义能，工程有坑** | LLM 往返（百 ms~秒）远大于 RTT（20–100 ms），延迟不是问题；真问题是幂等、取消、流式输出、审批位置与超时 |
| P4 | 用 P2P/UDP 自己组网 | **能用，但不该自研** | 现有 WebRTC/ICE/UDP 已是该问题的工业解；裸 UDP 可靠层在 v0.4 已被否决（3–6 人周 + 长尾 bug） |
| P5 | 公网 Server 心跳 + 加密传输兜底 | **已有，但有硬顶** | Bridge 只做 presence、coturn 盲转发密文；3Mbps 只够 1–2 路满速，见 §3.3 |
| P6 | 吸收鸿蒙软总线实现多设备流转 | **只能借思想** | DSoftBus 无公开 API；三方可用的是 `distributedDeviceManager` 等能力模块，且有多设备数/场景限制。见 §5.6 |
| P7 | 用户随时切换主节点、拷贝工作区接力 | **拆成两件事** | UI 漫游近免费；大脑迁移需冷迁移，且只有 PC↔PC 有意义（手机跑不了 DSH）。见 §5.5 |

> **P1 的边界要说清**：可分布式的是"工具执行"，不是"思考和上下文"。DSH 的 agent 循环、会话、审批都活在宿主进程里；跨机器只有一个大脑时，一致性、成本、冲突解决都是免费的。多大脑要解决共享上下文、任务分发、冲突合并、计费与权限——那是另一个产品。

## 2. 市面是否已有类似产品

### 2.1 四层盘点（只列与构想有实质重叠的）

| 层 | 产品 / 项目 | 它解决什么 | 与本构想的重叠 | 明确缺口 |
|---|---|---|---|---|
| 组网 | [Tailscale](https://tailscale.com/docs) / [Headscale](https://headscale.net) | WireGuard 网状网 + NAT 穿透 + DERP 中继 | 池的 L3 底座，含"公网兜底" | 不懂 agent、不懂工作区 |
| 组网 | [KDE Connect](https://invent.kde.org/network/kdeconnect-kde) / [LocalSend](https://github.com/localsend/localsend) | 局域网设备发现 + TLS + 文件/远程命令 | 设备池的用户体验原型 | 仅局域网、不可编程、无 agent |
| 组网 | HarmonyOS 超级终端（2021，华为） | 分布式软总线、设备虚拟化、任务流转 | 构想的直接思想来源 | 系统独占，无三方 API |
| 远程工作区 | [VS Code Remote-SSH / Tunnels](https://code.visualstudio.com/docs/remote/remote-overview) | 远端执行 + 本地编辑；Tunnels 免 SSH 出站中继 | "远程过程本地化"的成熟形态 | 单服务器、单客户端、无 agent 自主调度 |
| 远程工作区 | [Coder](https://coder.com/docs) / [Gitpod→Ona](https://ona.com) | 自托管云开发环境 | 工作区定义与生命周期 | 服务器中心、无 P2P、非自有设备 |
| agent 执行 | [E2B](https://e2b.dev) / [Daytona](https://www.daytona.io) | 云沙箱/microVM 给 agent 跑工具 | 远程工具的现成形态 | 单沙箱、在云上、非你的设备 |
| agent 执行 | [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)（2026） | 手机/浏览器接管**本机** session，执行仍在本机 | 与 RemoteDSH v1 几乎同构 | host 固定、无主节点切换、跨 session 只能发纯文本 |
| agent 执行 | [Happy](https://happy.engineering)（2025，开源） | 手机控自有电脑上的 coding agent，E2E 中继 | 与 RemoteDSH v1 同构的开源近似 | 一机多端，不是多机池 |
| agent 执行 | [Claude Managed Agents](https://claude.com/resources/articles/claude-managed-agents-updates)（2026-05） | 云 agent loop + 自托管沙箱 + MCP tunnels | "出站单连接暴露内网工具"的范式 | 单沙箱、无多设备 |
| 编排 | [Ray](https://docs.ray.io) / [KubeEdge](https://kubeedge.io) | 分布式/云边任务调度 | "设备池"的调度类比 | 任务级，无 agent/工作区语义 |
| 协议 | [MCP](https://modelcontextprotocol.io/specification) | agent↔工具，stdio / Streamable HTTP | 远程工具的事实标准 | 无 P2P binding、无文件原语、无设备目录 |
| 协议 | [A2A](https://a2a-protocol.org) | agent↔agent，Agent Card + Task | 多大脑路线的基础 | 需 HTTP 可达、无设备/工作区概念 |

### 2.2 缺口交集：没有任何现成产品做到的七件事

1. **同一 agent 会话在多台自有设备上并行调工具**——跨机目前只到"发纯文本消息"。
2. **主节点可随时切换**：Remote Control 绑固定 host；云 session 是把任务搬到云 VM，不是搬到另一台自有设备。
3. **P2P 组网与 agent 运行时解耦**：网络产品不懂工作区，agent 产品全走厂商中继。
4. **工作区接力**：Handoff / 鸿蒙搬的是 App 任务状态，远程开发映射单个固定工作区，都搬不了"运行中 agent + 未提交改动"。
5. **由 agent 主动发起的跨节点文件原语**：文件产品靠人点，MCP/A2A 都没有该原语。
6. **设备/工具能力目录**：A2A 目录的是 agent，不是"哪台机器有哪个工作区/工具"。
7. **断网降级与主节点切换后的一致性**：无标准。

### 2.3 为什么这个空白存在（这决定了立项语气）

- **云沙箱更省事**：模型厂商（E2B/Daytona/Managed Agents）把"agent 执行环境"做成云服务，用户零配置。
- **平台厂商做系统级连续性**：Apple Handoff、华为超级终端已覆盖"任务流转"的消费级场景，但三方不可编程。
- **多设备用户是窄众**：真正同时开着 2–3 台开发机的用户比例低，且他们今天用 SSH + Tailscale + tmux 也能凑合。
- **结论**：差异化必须落在"**自有设备 + 数据不过云 + 断网/内网可用 + 与 DSH 深度集成**"，而不是"更快的传输"。

## 3. 现有工程能给你什么，以及三条硬边界

### 3.1 可复用资产

| 组件 | 位置 | 池化后 | 复用代价 |
|---|---|---|---|
| 契约 + 四端实现 + 共享向量 | `remotedsh-contract/`（JS/Go/Kotlin/Dart） | 帧编解码、hello 签名、QR、fp 测试向量直接复用 | 低；池语义要新向量 |
| L4 隧道（11B 帧/信用/128 流/半关闭） | `dsh-mobile-link/lib/tunnel.js`、`rtc.js` | 作为"节点间字节泵"直接可用 | 低（单对）；池化需外层调度 |
| pair / hello 生命周期 | `dsh-mobile-link/lib/index.js:104-170`、`remotedsh-bridge/internal/hub/lifecycle.go` | 设计可借；模型要改（见 §3.2） | 中 |
| Bridge 信令 + coturn 部署 | `remotedsh-bridge/`、`deploy/DEPLOY.md` | presence/候选中继/TURN 凭证复用 | 低 |
| Android / 鸿蒙两线端侧 | `remotedsh-android/`、`RemoteDSH-flutter/` | 手机入口继续用；Node 可借 Dart/Kotlin 参考实现 | 低 |

### 3.2 硬边界一：pair 是 1:1 写死的，不是配置项

- 契约 **§4.3 销毁条件 ④⑤**：新手机对同一 agent `pair.bind` → 旧 pair 销毁；手机对另一 agent `pair.bind` → 旧 agent 的 pair 销毁。契约 §4.3 配对数约束原文：**"每 agent 至多 1 个 pair，每 phone 至多 1 个 pair"**（`new_docs/00-接口契约(2).md:197`）。
- 代码同样是单值结构：`Pair{PairID, AgentID, AgentBootID, PhoneID}`，`agents[agent_id]` 与 `phoneIndex[phone_id]` 各只存一条（`remotedsh-bridge/internal/hub/hub.go:46-70`）。插件侧状态也是单个 `pairActive/pairId/pc/tunnel`（`dsh-mobile-link/lib/index.js:74-87`）。
- 另有跨 pair 路由禁令："`pair_id` 一致性断言失败 → 回 `PAIR_NOT_FOUND`，**不得跨 pair 路由**"（契约:251）。

**含义**：主节点无法在现有契约下同时挂 N 个子节点。池化必然是一次**拓扑级改动**（契约 v2.0 或多身份映射），不是加字段。

### 3.3 硬边界二：3Mbps 中继是物理硬顶

| 量 | 值 | 出处 |
|---|---|---|
| 线路 | 3 Mbps ≈ **375 KB/s** | `new_docs/02-服务端实施方案(2).md:20` |
| coturn 整机上限 `bps-capacity` | **350 000 B/s**（2.8 Mbps） | 同上:146 |
| coturn 单会话 `max-bps` | **250 000 B/s**（2 Mbps） | 同上:147 |
| 满速并发中继会话 | **≈1.4 路** | `new_docs/02:45` 的"1–2 路" |
| N 节点全中继时每节点 | **350/N KB/s**（N=2→175，4→88，10→35） | 由上式推导 |

结论：**中继是控制面兜底，不是数据面通道**。文件搬运若走中继：100 MB 工作区 ≈ 4.4 分钟（理想），加上双端限速与 TCP 慢启动，实际更差。

### 3.4 硬边界三：地基还没稳，池会放大不稳定

- `changelog/ISSUES.md`：`ISS-009`（relay-only 是否消除周期断线）验证中；`ISS-014`（周期断线根因）未解决；`ISS-015`（白屏）、`ISS-020`（四功能未验收）未解决。
- 实测口径：`changelog/2026-09-20-028-…md:57` 记录"约 27s–2min 一次断线、恢复 3.6–6 s、**约 20% 时间隧道是死的**"。
- 若单链路可用率 0.8，则 N 节点池"至少一跳是死的"概率 = `1-0.8^N`：N=2 → 36%，3 → 48.8%，4 → 59%，5 → 67%。**池的可用性上界就是 0.8^N**。
- 更麻烦的是：`changelog/029` 之后双端走 relay 锚定，等于把全部流量压回 3Mbps——与 §3.3 直接打架。

**判断：多设备池不能长在现在的隧道上。** 要么先关掉 `ISS-009/014/015/020`，要么池的第一版用**别的传输**（见 §5.1）。

## 4. DSH 侧的接入面（决定"不改 DSH 能不能做"）

核实对象：DSH **0.1.5-rc.3**；仓库内 `Document/dsh-remote-research/06` 基于 0.1.2-rc.1，差异已复核。

| 问题 | 判定 | 证据 |
|---|---|---|
| 插件能否注册工具 | **能**，返回 disposer，运行时增删，emit `tools/change` | `dsh-tools/lib/types/index.d.ts:596`、`lib/index.js:2773` |
| 工具作用域 | host ctx → 全局层；agent.ctx → 该 agent 层（scoped 覆盖 global） | `scopeOf` |
| MCP client 传输 | 仅 **stdio / streamable-http**（无独立 SSE） | `dsh-mcp-client/lib/index.js:40-50` |
| MCP 动态/按会话挂载 | **能**，官方范例 `agentCtx.plugin(McpClient, cfg)` | `dsh-acp/lib/index.js:216` |
| MCP 工具命名 | `mcp__<serverName>__<rawName>`，超 64 字符追加 12 位 sha256 | `dsh-mcp-client/lib/index.js:120-126` |
| MCP 工具是否默认审批 | **否**。走 `tools/pre-execute`，无人返回 `{kind:'ask'}` 就不审批 | `dsh-tools` `resolveAsk` |
| DSH 能否当 MCP server | **不能**（全树 grep 0 命中） | — |
| 多客户端并发 | **能**。每连接一个 `clientId`，事件广播全体；审批 waterfall 投全部在线客户端，**首答生效、其余 cancel**；会话全局共享 | `dsh-api-gateway/lib/index.js` |
| 插件网络能力 | 能开 webServer 路由/upgrade；出站不受沙箱过滤 | `dsh-host-webserver/lib/index.js:176-196` |
| shell + 远端 CLI 兜底 | **成立，零 DSH 改动** | `dsh-base` patch 246–252 |

**结论**：不 fork DSH 完全可行。接入面从省到贵：**MCP 配置行 < 自定义工具 bundle < shell+CLI < ACP < 自建认证 HTTP**。其中 MCP 自动获得命名空间与重连，是最省的"远程工具"接口。

## 5. 推荐架构

### 5.1 三条原则

1. **单大脑**：agent 循环只有一个，跑在常开的 PC/服务器上；分布式的是工具执行面。
2. **星型拓扑**：主节点 ↔ 每个子节点一条链路（N−1 条）；不做全互联（N(N−1)/2 对，N=4 就要 6 次打洞）。
3. **传输可替换**：池层只依赖 `TransportAdapter` 接口（`open(node) → duplex stream`），第一版实现 SSH / Tailscale，第二版才是自有隧道。**这是把"未稳定的隧道"与"未验证的池价值"解耦**，也是本方案最重要的工程判断。

```
                      ┌──────────── 主节点（常开 PC / 服务器）─────────────┐
                      │ DSH web 进程 —— 唯一 agent 大脑                     │
                      │  ├─ pool-hub：节点注册表 / 能力目录 / 健康 / 路由     │
                      │  ├─ N × MCP client：mcp__pc2__* … mcp__pc3__*        │
                      │  └─ dsh-mobile-link：手机 UI 的既有 1:1 隧道（不动）  │
                      └──────┬──────────────────────────┬──────────────────┘
      TransportAdapter：(1) SSH/Tailscale 先    │                  │
      (2) 自有隧道 / 池信令 后                  │                  │
                       ┌─────┴──────┐      ┌────▼─────┐      ┌─────▼──────┐
                       │ 子节点 PC  │      │ 子节点 PC│      │ 手机（UI） │
                       │ dsh-node   │      │ dsh-node │      │ WebView    │
                       │ └ MCP srv  │      │ └ MCP srv│      │ 13080 本地代理│
                       └────────────┘      └──────────┘      └────────────┘
```

### 5.2 组件与"要搭建的远程工具"

| 组件 | 职责 | 形态 | 工作量 |
|---|---|---|---|
| **`dsh-node`**（接收远程过程） | 暴露 MCP server（exec / fs / transfer / job）；能力清单；本地审批与审计；长任务 job 管理 | 独立守护进程（Node），PC 常驻；手机只能前台受限运行 | 1.5–2 周 |
| **`pool-hub`**（远程过程本地化） | 节点注册表、能力目录、TransportAdapter、N 个 MCP client 挂载、健康探测、路由 | `dsh-mobile-link` 插件内新模块（可复用 `ctx.tools.register` / `ctx.plugin(McpClient)`） | 2–3 周 |
| **`pool-transfer`**（文件传输） | 分块 + sha256 + 断点续传 + 忽略规则；小文件直接流、大目录走 git bundle | 复用隧道 stream 或 SSH 管道 | 1 周 |
| **`pool-ui`**（管理面） | 节点列表、入池、授权、健康、接力入口 | DSH web 插件页（`ctx.webServer.register`） | 1 周 |
| **不需要** | 分布式文件系统、自研 UDP 可靠层、全互联 mesh、DSH 内的 MCP server、多大脑调度 | — | 0（省下来的时间） |

**用户直觉里的三件套是对的**，但漏了两件关键的：**节点注册表/能力目录**（没它 agent 不知道"有哪些设备、能干什么"）与**审批/审计**（没它池就是后门）。

### 5.3 关键设计 A：为什么不做"多个磁盘"（VFS）

- OS 挂载（WinFsp/ProjFS/FUSE）会让每个 `stat`/`readdir` 变成一次网络 RTT；在 20–100 ms、偶发断线的链路上，`node_modules` 规模的目录遍历会从毫秒级退化到分钟级，且工具调用失败语义变成"文件系统卡住"。
- 手机（鸿蒙/iOS）三方应用无法挂载远程 FS。
- 业界同类（VS Code Remote、Coder、Mutagen、E2B）全部选"**远程执行 + 工作区同步**"，无一选择挂载。
- **替代方案**：路径即命名空间 + 显式搬运。工具签名里带节点即可：
  ```text
  mcp__pc2__exec({ cmd, cwd, timeout_ms, idempotency_key })
  mcp__pc2__read_file({ path })
  pool_transfer({ from: "pc2:/repo", to: "pc3:/repo", paths: [...], mode: "push"|"pull" })
  ```
  模型看到 `mcp__pc2__*` 与 `mcp__pc3__*` 两组工具，等价于"两个磁盘"，但每次操作都是显式的、可审计的、有超时的。

### 5.4 关键设计 B：远程过程 = MCP client 挂载（零新协议）

- 子节点 `dsh-node` 在自己 loopback 上跑 **Streamable HTTP MCP server**（`/mcp`）。
- 主节点 `pool-hub` 通过 `TransportAdapter` 把该端口映射到主节点本地的 `127.0.0.1:<portN>`（与手机本地代理同构，只是方向相反）。
- `pool-hub` 为每个节点 `ctx.plugin(McpClient, { serverName: "pc2", transport: "streamable-http", url: "http://127.0.0.1:<portN>/mcp" })`，工具自动出现为 `mcp__pc2__*`。
- **收益**：命名空间、重连、工具表同步、`tools/change` 全部由 DSH 现成实现；池层不碰工具语义。
- **必须补的坑**：①MCP 工具**默认不审批**→ `pool-hub` 必须注册一个 `tools/pre-execute` listener，对跨节点执行返回 `{kind:'ask'}`（审批落点见 §5.7）；②默认 60 s 超时 → 长任务改 `job` 模式（提交返回 job_id，轮询/订阅），不要让一个 tool call 扛整段传输；③工具名 64 字符上限 → 节点名限 8–16 字符。

### 5.5 关键设计 C：接力拆成"UI 漫游"与"大脑冷迁移"

| 类型 | 用户看到的 | 实现 | 成本 | 限制 |
|---|---|---|---|---|
| **UI 漫游**（推荐先做） | 在手机上聊到一半，打开笔记本继续同一会话 | DSH 已支持多客户端并发：事件广播全体、审批首答生效其余 cancel、会话全局共享（`dsh-api-gateway`）。笔记本只需一个"入口客户端"（proxy 到主节点 DSH） | **数天**（PC 端一个小代理） | 大脑不搬家；笔记本必须能连到主节点（LAN 或同一隧道体系） |
| **大脑冷迁移**（可选，PC↔PC） | 在家用台式机，出门切到笔记本，agent 在新机器上继续 | 拷贝 `~/.dsh`（会话 zstd + 配置 + 身份） + 工作区（git bundle / 分块同步） → 在新机器启动 DSH → 重新入池 / 重新配对 | 1–2 周 | **不是热迁移**：运行中的命令、PTY、后台任务、待审批项、沙箱状态全部丢失；OS/DSH 版本差异要处理 |
| **热迁移** | 无感搬走正在跑的 agent | — | 不建议 | 见 §7 |

**重要事实**：手机跑不了 DSH（Node.js 运行时不存在，鸿蒙/ iOS 三方应用也没有常驻能力），所以"切换到手机当主节点"只能是**切换到手机当入口**。用户愿景里的"随时切主节点"应表述为"**入口可换，大脑不动**"。

### 5.6 关键设计 D：鸿蒙软总线——借思想清单

| 软总线做法 | 三方可用性（事实） | 池里怎么借 |
|---|---|---|
| DSoftBus 组网 | ❌ 无公开 ArkTS API，`conversation` 标系统接口 | 自建 TransportAdapter；近场（LAN/mDNS）优先，公网中继兜底 |
| 设备发现 | ✅ `distributedDeviceManager`（API 10），需 `DISTRIBUTED_DATASYNC`；发现要求同局域网或蓝牙，单次 2 分钟/≤99 台 | 发现＝bridge presence + 局域网 mDNS；WAN 用池注册表 |
| 可信配对 | ✅ PIN 绑定、持久可信列表 | 沿用现有 QR + DTLS 指纹 pin；节点侧改为**长期入池凭证**（见 §6 的坑） |
| 能力描述 | 系统内部 | 自建 capability manifest：OS/arch/工具集/工作区根/资源余量 |
| 任务流转 | ⚠️ `onContinue` 可写但"迁移触发由系统应用完成" | 只借"**状态快照 + 目标端重放**"语义，不搬连接 |
| 分布式数据对象 | ⚠️ 官方限定"跨端迁移/跨设备 Call"，≤3 设备、150 KB/500 KB | 不能当设备池通道；只能做小状态同步 |

**一句话**：软总线是"系统级设备虚拟化"，我们是"用户态工具虚拟化"。思想可借：**近场优先 + 可信配对 + 能力清单 + 快照式迁移**；API 借不到，不要指望。

### 5.7 关键设计 E：安全模型（这是产品级工作量）

| 界线 | 现状 | 池必须补 |
|---|---|---|
| 入池信任 | 现有 QR + pair_token（一次性、TTL 5 min） | 节点长期凭证（重启不掉线）+ 撤销列表；**pair 模型不适合无人值守节点**（见 §6.1） |
| 权限 | DSH 单 cookie、无设备表、无按设备撤销 | 每节点工具白名单（允许 exec 的目录/命令前缀）、只读节点、沙箱策略 |
| 审批落点 | 审批投给所有在线 UI，首答生效 | **命令在哪个节点执行，审批就应在哪个节点产生**（或至少显示执行节点与命令全文）；主节点的一个误批不能静默扩散到 N 台 |
| 幂等 | 无 | exec 必须带 `idempotency_key`；重试策略按命令分级（只读可重试，写/删不可重试） |
| 审计 | 插件与 Bridge 滚动日志 | 执行节点本地审计（谁、何时、哪条命令、结果哈希），主节点汇总 |

## 6. 分阶段路线（每阶段都有独立价值）

### 6.1 先说一个必须先解决的坑：pair 不适合节点

契约 §4.3 条件②：同一 `agent_id` 重连但 `boot_id` 不同 → 销毁 pair，手机收 `AGENT_RESTARTED`。对手机场景这是对的（DSH 重启 = launch token 失效）。对**无人值守节点**是灾难：守护进程每次重启/升级/重启机器，配对就没了，需要人重新扫码——N 个节点不可运维。

三条出路（按推荐顺序）：
1. **池不走 pair**：节点用 SSH/Tailscale（稳定身份，无常驻配对状态），隧道只服务手机 UI。**推荐**。
2. **池模式进 Bridge（契约 v2.0）**：引入 `pool` 对象与长期成员凭证，pair 退化为"手机入口"，节点成员身份与 `boot_id` 解耦。
3. **节点侧持久化 `boot_id`**：技术上可行，但违反契约语义（`boot_id` 的定义就是"是不是同一个进程"），会污染现有语义，不推荐。

### 6.2 阶段表

| 阶段 | 目标 | 交付物 | 验收 | 工期 | 依赖 |
|---|---|---|---|---|---|
| **P0 单节点闭环** | 证明"agent 能操作另一台机器"有价值 | `dsh-node`（MCP: exec/fs）+ `pool-hub` 最小版 + SSH 传输；1 个远端节点 | agent 在节点 B 上执行命令、读文件、返回结构化结果；审批可见命令全文 | 1–2 周 | 无（不碰契约） |
| **P1 池骨架** | 多节点、能力目录、权限 | 节点注册表、capability manifest、per-node 白名单、审计日志、`pool_nodes()` 工具 | 3 节点；节点重启自动恢复；越权命令被拒 | 2–3 周 | P0 |
| **P2 文件与工作区** | 跨节点搬代码 | `pool-transfer`（分块 + sha256 + 续传）+ `pool_sync`（git bundle） | 100 MB 仓库同步成功、可续传、校验一致 | 1–1.5 周 | P0 |
| **P3 接自有隧道** | 摆脱 SSH/Tailscale 依赖 | `TransportAdapter` 第二实现（N 个 answerer + 现有帧协议）；桥接手机入口 | 2 节点在纯公网无 SSH 环境打通；P2P/TURN 比例可观测 | 3–4 周 | **ISS-009/014/015/020 关闭** |
| **P4 UI 漫游** | 多入口同一会话 | PC 端入口客户端（代理到主节点）+ 会话并发验证 | 手机与笔记本同时看同一会话；审批首答生效、另一侧取消 | 1 周 | P1 |
| **P5 冷迁移**（可选） | PC↔PC 搬大脑 | `pool_handoff`（`~/.dsh` + 工作区 + 重启 + 重新入池） | 迁移后会话可继续；文档写清丢失项 | 1–2 周 | P2/P4 |

**关键排序理由**：P0–P2 完全绕开"链路稳定性"与"契约 1:1"两个雷，先验证池的价值；P3 才是真正的投入决策点。如果 P1 阶段发现用户其实只需要"一个大 PC + 一个手机"，那 P3 就不该做。

## 7. 明确不做（YAGNI 清单）

1. **分布式文件系统 / FUSE 挂载**——延迟与失败语义双输，手机不可用。用"命名空间 + 显式搬运"代替。
2. **自研可靠 UDP/QUIC 栈**——v0.4 已否决（3–6 人周 + 长尾 bug），WebRTC 已是工业解。
3. **全互联 mesh**——星型够用；mesh 的连接数、打洞次数、状态同步成本与收益不成比例，等真出现"节点间大流量直传"再说。
4. **多大脑（分布式 agent 协商）**——共享上下文、冲突解决、计费、权限都没答案；先用"单大脑 + 多执行面"，需要时再引入 A2A 子 agent。
5. **热迁移 / 运行中进程搬家**——CRIU 级工程，收益极低（LLM 调用本身在云上，本地进程状态价值有限）。
6. **完整账号体系**——先用"设备入池凭证 + 撤销列表"，`v0.4 §1.3` 已把它列为非目标。
7. **手机作为执行节点**——系统限制明确（后台断网、无通用 exec），手机只做入口/受限能力（文件、分享、传感器）。
8. **在 DSH 内造 MCP server**——DSH 明确没有该面；需要时用 ACP/SDK/HTTP `/api`。
